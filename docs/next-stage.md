# InfiniDojo 下一阶段：围绕交互生成可定制操作评测场景

更新：2026-10-13。状态：**开发诊断已开始，尚未执行本阶段正式实验**。

本文件约定下一阶段的工作顺序、交付物、比较方法和验收标准。
它不替代 [v0 冻结协议](evaluation.md)，也不修改 [v0 实验结果](../results/v0-pilot/README.md)。
正式实验参数须在开发集校准后另行冻结，下述建议网格不是已执行结果。
研究主张、有限范围和停止条件以 [投稿版本约定](paper-contract.md) 为准。

## 1. 论文主线与研究问题

**按评测需求生成不同场景复杂度的 RoboDojo 操作实例。**

沿用 InfiniBench 可定制 benchmark generator 的动机和语言约束前端思路。
操作领域需要布局支持完整交互过程。核心方法是：在最小任务场景中建立参考操作，
按 interaction event 组织机器人与物体的关系，再围绕这些关系生成完整场景。
失败模式分析和 RSI 保持为下游用途；参考轨迹不要求被测策略模仿。

论文的主要主张是：**提供可定制的生成流程，产出可用于操作策略评测、且经过物理验证的实例。**
生成产出率和效率用于刻画系统及方法，不把“相同预算下超过所有基线”作为主要结论。
这项能力要在声明的任务/条件范围内批量展示，而不是仅证明能生成几个成功实例。
“RoboDojo 上没有类似系统/首次实现”须另做相关工作和已有配置/随机化能力核查，暂不作为事实。

> 场景描述与任务 → 程序化约束 → 最小任务场景与参考操作 →
> event-conditioned cluster 场景补全 → 共同物理验证 → 可运行的评测 episode。

- RQ1（主要）：能否按指定复杂度批量生成符合要求、可执行、可复现且可直接评测的实例？
- RQ2（方法证据）：event/cluster 对条件表达、关系保持与完整操作支持有何作用、代价和边界？
- RQ3（应用）：OpenWAM 与 GPT-6 Astra 在原生 RoboDojo 实例和生成实例上的表现有何差异，
  生成流程提供了哪些可明确控制的评测条件？

## 2. 最小方法及范围

### 2.1 任务与 Infinigen 资产

首选完整任务为 RoboDojo 原生 `stack_blocks`：包含多次接近、抓取、搬运、放置和撤离，
也能检查已放置物体对后续操作的影响。已检查
[v0 依赖中的任务实现](https://github.com/RoboDojo-Benchmark/RoboDojo/blob/726e9aabfaa642203722eb126f5eaf0f37f3e1ad/task/RoboDojo/tasks/stack_blocks.py)，原生成功条件包含
三个方块堆叠与机器人返回初始位置。实施时再核对标签、几何元数据、评分阈值和步数预算。
**只完成一次放置不能记为原生 `stack_blocks` 成功。**

先保留原生任务物体打通操作，使用 Infinigen 生成周围物体；再引入影响操作空间的
程序化宽度、高度变化及关联布局。目标资产的替换须通过几何元数据、支撑和评分契约检查。
统一缩放不等于覆盖形状变化，闭合物体的凸包导出器不能直接用于有开口的容器。

若开发阶段发现完整堆叠的接入成本掩盖生成问题，可以先做单物体放置诊断，
但必须命名为独立的 InfiniDojo 扩展任务，另写评分规范，不替代原生堆叠结果。
正式主任务调整须在冻结前说明理由，不能根据测试集结果换任务。
`general_pickup` 先作为回归检查，随后与 `cover_blocks` 补充论文任务覆盖。
`cover_blocks` 必须包含按顺序覆盖、按颜色揭开及返回初始位置，不能只完成覆盖阶段。
另外两个任务的原生判定已核对并记录为 [general_pickup 契约](../specs/tasks/general_pickup.json)
和 [cover_blocks 契约](../specs/tasks/cover_blocks.json)。覆盖任务还有方块位移超过 5 cm
即失败的约束；覆盖判定使用外部包围轮廓，不能代替杯腔的物理有效性验证。
`general_pickup` 现已有两个原生罐体位置的完整参考、G2 六杂物补全、26 项独立开发检查及
episode 导出/重载证据，见 [拾取开发结果](../results/v1-pickup-development/README.md)。
其预算内 G1/G2/G3 及一次目标位置修复也已接入，七组开发运行有完整记录，见
[拾取统一生成结果](../results/v1-pickup-retry-development/README.md)。语言入口和策略执行尚未完成。
`cover_blocks` 已完成原生六次搬运参考，
一个六杂物 G2 实例通过 29 项开发检查，包括覆盖/揭开顺序、实际接触及整个方块体积的
杯腔源网格检查；导出后在新目录加载重放仍通过，见
[覆盖开发结果](../results/v1-cover-development/README.md)。
覆盖任务的语言、场景感知 G1/G3 和真实策略评测仍未接通。

### 2.2 Event：关系在何时切换

每次操作至少包含 `approach → grasp → transport → place → retreat`，记录：

- 参与对象、开始/结束条件，以及阶段之间共享的状态；
- 合法接触对、支撑关系和抓取建立/解除条件；
- 连杆、夹爪、操作物体的运动与空间占用。

各阶段使用同一初始场景，连接动作也参与检查。抓取前目标由原支撑面承载；
持物时随夹爪运动；释放后留在新支撑面，并继续参与后续碰撞检查。
计划中的附着关系不能替代真实夹持验证，不得在执行时焊接或瞬移目标来保证成功。

### 2.3 Cluster：哪些对象需要关联调整

interaction cluster 是共同受运动/接触/支撑约束的对象集合，不是单一刚体。
机械臂各连杆沿关节轨迹运动；仅在稳定抓取时保持物体与夹爪的相对关系。
几何检查使用各部分，不将整个机械臂和目标合成一个巨大刚性盒子。
静态场景 cluster 保留已声明的支撑、容纳或邻接关系。

第一版只考虑两类布局操作：

1. 在允许区域内移动或重采样周围物体/cluster，保持内部关系及用户要求。
2. 固定交互限制指定布局时，有限次修改允许变化的抓取/放置位置等任务参数，
   用现成规划器更新动作，同步更新受影响的阶段及其连接。

第二项按开发实验暴露的问题实现，不预设通用联合优化器。固定底座时不能直接平移
机械臂轨迹冒充重新求解。如果第一项与固定轨迹空间预留等价，应作为简单基线处理，
不能仅凭 event/cluster 名称宣称新算法。先不增加学习模型、新运动规划器或复杂缓存调度。

### 2.4 约束与修复边界

硬约束包括任务语义、数量、资产范围、布局区域和指定关系；可调变量及范围必须显式列出。
修复不能删杂物、扩大区域或将物体缩小到范围外。预算耗尽就记录失败。
除总数外，检查目标附近密度/距离和区域占用，避免把全部杂物移远来满足操作。

Infinigen 的资产、几何参数和必要关系接口按需接入，不要求重写完整求解器。
语言前端负责约束/事件编译及反馈修正；其是否构成独立贡献取决于消融证据。

## 3. 必须实现的生成对照

**G1 — generate–plan–retry。** 在请求约束内生成静态合理场景，再用共用规划器尝试完整任务；
失败后在总预算内重采样。允许针对新场景重新规划，不要求执行我们的参考轨迹。

**G2 — fixed-trajectory completion。** 在最小任务场景获得参考操作后固定动作，
围绕完整运动空间补全场景。包含持物后的目标几何、合法接触、放置和撤离过程；
不能故意删掉这些信息制造弱基线。这是 v0 思路在完整任务上的强版本。

**G3 — event-conditioned cluster generation。** 使用同样的资产、任务和规划器，
按第 2 节关联调整场景。任务位置更新和重规划受相同总预算限制。
记录每次变更、受影响阶段、规划次数和接受/拒绝原因。

这些对照支撑方法解释，不以必须赢得效率竞赛作为系统贡献的前置条件。
三者共享请求、资产候选、参数范围、机器人、评分、验证器及种子组。
涉及产出/成本的比较使用相同端到端时间预算，并报告规划/仿真次数和候选次数上限。
不同成本的“一次尝试”不能当作等价预算。共用前端后的几何比较与语言实验分开。

必做消融：G3 禁用任务位置更新/关联修复，检验是否退化到 G2。
如禁用 event 表示，仍允许基线根据实际逐帧姿态检查全轨迹并允许任务必要接触；
不能故意禁止抓握来制造失败。不存在有意义的独立开关时，说明组件耦合。
LLM 一次生成与反馈修正在多样的真实描述上比较，人工注入错误仅用于接线诊断。

当前堆叠语言前端已接入真实模型及生成器。十二条开发描述的第一次与最终答案一致，
没有触发修正；正确答案只用于事后评分。一个编译结果已完成物理生成和导出，见
[语言前端开发结果](../results/v1-language-development/README.md)。此结果支持受限接口可用，
不能作为迭代收益或任意任务语言规划的证据。

这些是受控自建对照；未经适配与运行，不称为 InfiniBench/Sceniris 等论文的复现。

## 4. 共同验证与指标

### 4.1 接受口径

共用验证器读取最终资产和实际物理状态，检查请求符合度、初始化、原生完整任务结果，
以及任务规范下的非法接触/穿透；不能直接信任生成器输出的“无碰撞”或简化包围盒。
所有方法均可在同等验证预算内调用共用求解器重新规划。
参考重放与重新规划结果分别报告，任何完成证据都须经实际物理执行。
候选自带参考轨迹的计算同样计入生成成本，验证成本计入总预算。

使用仿真接触/穿透记录与更精细几何检查相互校验；合法接触集合由任务规范定义，
不能由生成器为自身结果临时放宽。阈值、采样分辨率及稳定保持时间在开发集校准后冻结。
抽查接受/拒绝样本的视频与轨迹，报告几何近似误判，不声称采样检查证明连续无碰撞。

未找到完成方式记为 `unverified`，不直接判为物理上不可解。
部署、模型服务或仿真基础设施故障单独标记，不混入策略能力失败。
全请求分母保留所有实例，另报有效基础设施条件下的结果；重跑保留原始尝试。

### 4.2 指标与统计

主要证据由条件可控性、物理有效性、覆盖/多样性与直接评测能力共同组成，不用单个效率分数替代。

- **有效性：** 满足请求且通过共同物理验证的实例数 / 全部请求数，按任务和条件分别报告。
  有限预算需公开，用于界定实际能力；相同预算的相对优势是次级分析。
- **成本：** 每个有效实例的总耗时，包括资产生成、参考获取、规划、修复和验证；
  分别报告冷启动和复用资产/运行时的摊销成本，失败请求的计算不能丢弃。
- **忠实度：** 数量、几何范围、区域、关系及任务语义的逐项符合率。
- **覆盖/多样性：** 条件覆盖、几何内容差异、归一化布局差异和目标附近密度/距离分布。
  相同物体数不自动等于相同操作复杂度。
- **诊断：** event 失败位置、接触/穿透、初始化漂移、重规划次数、参考重放成功率。
  v0 包围盒审计可作为诊断，不继续充当唯一有效性判定。

按共享场景/资产种子做配对分析，复杂度档位作为同一组内的重复条件。
报告种子级差值和以种子为单位的置信区间，不把同种子条件或轨迹帧视为独立样本。
真实策略得分与参考控制器的验证成功率分开报告。

数量、几何档位、布局/关系范围和时间预算须先在开发集检查可表达性。
建议网格可在 P0–P2 调整，但要在冻结记录说明，不根据测试结果删档位或换种子。
样本量是本阶段起点，不自动构成充分统计证据；后续确认实验使用新的预留种子。

交付：冻结协议、原始结果索引、成本/覆盖报告、图表和复现命令。
验收：全部请求有去向，结论区分支持、无明显差异和证据不足。
首要结论是声明范围内生成能力是否成立；如进一步主张相对优势，须与条件忠实度和覆盖一起报告，
不能靠降低实际拥挤程度取得优势。方法无相对优势不自动否定系统能力，但须收缩算法创新表述。

### P4 — 两个策略 × 两类实例的评测比较

四组为 OpenWAM 在原生集/生成集、GPT-6 Astra 在原生集/生成集的结果。
这项实验回答扩展后的评测条件如何刻画两个策略的表现；生成方法之间的比较属于 P2–P3。

开发入口已接入原生 evaluator 的布局加载、RGB/本体观测及输入输出归档；原生相机诊断通过。
OpenWAM 已完成原生/生成两个开发实例的真实评测，两局均为 15/100，完整任务均未成功；
配置、动作和原生评分审计通过。Astra 首次配对因账号额度耗尽而中断，两局均无有效成绩。
完整比较仍未完成，见 [策略评测接入](policy-evaluation.md) 及
[开发证据](../results/v1-policy-development/README.md)。基础设施故障不计为策略任务失败。

- [ ] 按第 6 节接入 OpenWAM 与 GPT-6 Astra，冻结各自 checkpoint/服务、适配器和调用配置。
- [ ] 原生任务上检查真实相机、动作、控制时序、重置和评分链路。
- [ ] 冻结两个实例集合：原生 RoboDojo 实例，以及相同任务的 InfiniDojo 生成实例。
      原生集合涵盖所选任务已提供的标准/随机化配置并分层记录，不只挑容易的原生场景。
- [ ] 两个策略分别运行两个集合，均不接收参考轨迹、event 标注或生成器隐藏状态。
- [ ] 按任务报告原生成绩、生成集各条件成绩、每个策略跨集合的变化及两个策略之间的差异。

这里比较的是实例来源，执行平台仍然是同一 RoboDojo。每个策略在两组之间保持自身模型、
观测、控制适配和预算不变；任务语义、成功判定、机器人和任务权重对齐。
任务不一致的扩展实例单独报告，不直接并入原生对比平均数。

建议首轮规模：预先选定 18 个原生实例；生成集按固定种子顺序每档选最多 6 个已验证 G3 实例，
共最多 18 个。两个策略共享两组实例，共最多 **72 个首次评测 episode**。
选择不查看策略成绩，有效实例不足时报告短缺，不暗中补齐；原生集合的参考验证状态也需记录，
验证失败不静默删除。两组接受/排除规则公开，不把不同筛选条件伪装成严格配对。
这是选定任务子集的研究评测，不与官方全套排行榜成绩混称；如需完整榜单复现须另行执行。

两集合本来具有不同分布，跨集合成绩差值是描述性比较，不自动证明某单一因素导致下降，
也不能单凭更低分证明生成集更有价值。单因素解释需要在生成集内做受控变化，
能一一配对的变体才做配对统计。参考验证成功与策略评测成功分开。

交付：策略配置/来源、实际输入输出、原生得分、视频、故障和成本统计。
验收：两个真实策略各自完成两类实例评测（允许任务失败），dummy/空动作不算完成。
模型接入不阻塞 P0–P3；如其中一个受外部条件阻塞，记录缺口并保持对应论文实验未完成。

### GPT-6 Astra / XPolicyLab

- 用户提到的 GPT6 对应
  [GPT_6_Astra_Direct_EEF](https://github.com/XPolicyLab/XPolicyLab/tree/f6e309e8ece20bfa33c0e5d7b05a5f3287522757/policy/GPT_6_Astra_Direct_EEF)，

- 上游默认每 episode 最多 100 次模型调用、单环境，需具备服务访问条件。
  实验固定模型 ID、提示、工具、图像历史、调用数与 planner timeout。
  若采用已有 Codex 账号桥接版，单独命名并记录传输/提示差异，不当作官方 API 条件重跑。

### 共同报告要求

使用相同场景、任务语义、机器人、评分与预先规定的仿真任务预算。
分别记录模型调用、低层控制步、模拟时间和真实耗时，不能把模型调用数等同于动作预算。
保留各自必要的控制适配，但明确 planner 可访问的几何信息和工具权限。
比较对象是整套策略系统，动作接口/规划权限差异不能归因于基础模型能力。
相机/本体观测之外的隐藏参考动作、生成约束和验证信息不泄露给策略。

实例集及验证在观察策略成绩前冻结。不为单个策略选种子、改场景、延长失败 episode 或微调权重。
网络/服务/部署问题与正常决策失败分开，既报全部请求也报可用服务条件下的结果。
本阶段不要求两个模型分数拉开或排名变化。

## 8. 投稿版本的范围与停止条件

首版限定 `arx_x5`、`general_pickup` / `stack_blocks` / `cover_blocks` 三类任务、
至多两个 Infinigen 资产家族、三个生成对照和上述两个策略，见投稿版本约定。
条件范围在开发阶段确定，正式实验前冻结。
单任务起始实验与最终论文覆盖分开；不在结果出来后不断扩任务、资产或模型。

完成标准是：声明范围内可控生成能力有批量证据、物理有效性有独立验证、event/cluster 作用
有诚实的对照说明、两个策略的两组实例比较完成、代码与结果可复现。
不以 100% 生成成功、最高产出率、模型降分或排名反转作为投稿门槛。

按“开发诊断 → 一轮有明确问题依据的核心调整 → 冻结 → 正式实验 → 写稿”推进。
冻结后的继续工作只处理实现错误或直接影响主要主张的证据缺口，变更留记录；
新的规划器、更多任务、额外模型、RSI 和深入失败机理研究留给后续工作。
