# 拾取任务的统一生成流程：开发证据

日期：2026-10-13。原生直立罐体、一个开发种子、两档杂物数量的接入诊断。
这不是正式有效率实验，也不是 OpenWAM/Astra 策略评测。
全部七组配置在运行前写入 [开发约定](../../specs/v1-pickup-retry-development.json)。

## 全部结果

七组已全部完成，逐请求记录见 [request-rows.json](request-rows.json)。
每个子目录保留全部尝试、参考获取、接受检查与原始证据哈希，包含未通过的候选。

- 六杂物 G1：第三次候选通过，142.81 秒、53 次局部放置提案；前两次在下探规划失败。
- 六杂物 G2：首次候选通过，70.40 秒、17 次提案。
- 六杂物 G3：首次候选通过，63.46 秒、17 次提案；没有触发修复。
- 十二杂物 G1：四次候选均未通过规划，180.71 秒、464 次提案；布局次数预算耗尽。
- 十二杂物 G2：前两次未找到完整布局，第三次通过，68.89 秒、2,244 次提案。
- 十二杂物 G3：首次补全失败后，将目标从 `(0.22, -0.05)` 移到允许的 `(0.22, -0.11)` m，
  完整重规划并执行后，第二次候选通过；107.00 秒、1,550 次提案。
- 十二杂物 G3 禁用修复：第三次候选通过，65.69 秒、2,244 次提案。

六个接受的运行都通过 27 项检查并导出 episode，但仅对应
[四个不同布局](accepted-layout-groups.json)，不能当作六个独立生成样本。
各方法的输入、资产身份、初始位置、预算和实际执行源码一致，见
[比较检查](comparison-checks.json)。禁用修复后的参考控制/轨迹哈希、
三次非计时布局记录及最终布局均与 G2 一致，见 [消融核对](ablation-equivalence.json)。

这支持“有界生成与一次 event 归因修复已实际运行”的结论。
G3 本次减少了布局提案，但新增参考获取使总耗时更长；G2 同样生成了有效实例。
因此这些结果不能证明修复必需、生成效率更优或总体优势。

## 补齐的接口

`general_pickup` 现在接入与堆叠相同的有界生成执行器：

- G1 获取真实初始状态，生成场景，再用共用场景感知规划器执行；失败后在预算内重采样。
- G2 新建完整物理参考，围绕其完整运动空间补全场景，再重放和独立验证。
- G3 在补全失败时，按 event 记录的冲突为允许的目标位置排序，至多修改一次初始位置，
  随后重新规划并执行完整参考。禁用修复时保留首个参考，与 G2 使用相同流程。

三个方法使用相同资产身份、位置选项、采样器、物理验证器和预算。
目标仍为原生 `can/00000`，质量、摩擦、几何和初始高度均保持不变。
参考沿用已验证的前下方 45° 抓法，不宣称支持任意目标的抓取合成。
拾取以持续持物结束，因此修复依赖关联目标的来源位置，不增加放置或释放要求。

原先的持物代理为小方块预留 125 个覆盖球槽位，装不下长罐体。
现在在规划器初始化时按操作物体的实际范围分配容量；此罐体需要 350 个球。
保留原有 1 cm 网格单元，未截断几何或降低分辨率；静态杂物不占持物容量。
场景感知规划仍使用已有 CuRobo，包含目标、杂物、桌面、固定设施与另一机械臂。
规划模型中的持物附着不产生物理焊接；最终仍检查实际夹持、接触、抬升及稳定保持。

[独立规划探针](payload-probe/result.json) 在同一抬升目标处加入 14 mm 虚拟障碍：
保留持物几何时规划失败；仅诊断性关闭持物球后成功；移除障碍并恢复持物球后再次成功。
障碍距其余机器人代理几何约 13.61 mm。这个对照证明扩容后的罐体几何实际影响规划，
不是仅分配了未使用的数组；它不计作物理执行或生成样本。

## 开发条件与记录口径

请求分别为 6/12 个 Infinigen 杂物，三/六对、对内间距 9 cm，区域为
`[0.08, -0.14]` 至 `[0.50, 0.28]` m，物体间隙要求 3 mm。
目标可选位置为原始 `(0.22, -0.05)` m 及四个轴向 6 cm 偏移。
这些位置对三个方法相同；不得通过修改杂物数、资产或范围接受失败请求。

每组上限：240 秒、4 次完整布局尝试、共 4,000 次局部放置提案，
每个布局最多 1,000 次、每个杂物对最多 128 次提案。
每次物理执行最多 10,000 步；G3 最多一次目标位置修复。
时间包括重新获取初始状态/参考、进程启动退出、生成、规划、执行、验证和导出。
预生成资产的创建成本另记，不能把这些时间当作完整冷启动成本。

独立开发验证额外核对目标位置属于请求选项，拾取共 27 项检查。
不通过或未找到参考记录为未验证，不据此断言场景不可解。
各次参考来自独立仿真初始化；检查来源哈希，不能仅凭相同种子假定浮点轨迹完全一致。
不同条件是同一场景族的重复条件，尝试数和轨迹帧数不是独立样本数。

七组运行后修正了一处依赖记录：持物结束的拾取任务不应列出不存在的 `return/settle`。
这两项此前只出现在受影响阶段的文字列表，实际动作程序没有它们。
[离线复核](dependency-metadata-correction.json) 确认删除后排序、分数、选中位置均不变；
物理结果保留原始记录，不追溯改写。每次运行的源码哈希标识实际执行版本。
规划探针随后增加可选 event 与容量恢复，未改变七组运行。
57 项测试与代码检查通过；既有带位置选项的堆叠记录仍通过 25 项独立检查。

## 复现入口

先用现有输入脚本重建拾取布局，避免复制原生资产：

```bash
PYTHONPATH="$PWD/src" .venv/bin/python scripts/pickup_development_inputs.py \
  --robodojo-root "$ROBODOJO_ROOT" --output outputs/pickup-retry-reproduction/inputs

PYTHONPATH="$PWD/src" .venv/bin/python -m infinidojo.request_run \
  --method g1 --robodojo-root "$ROBODOJO_ROOT" --sim-python "$SIM_PYTHON" \
  --assets outputs/v1-development/assets/1200 outputs/v1-development/assets/1201 outputs/v1-development/assets/1202 \
  --request specs/requests/pickup-anchor-paired-6.json \
  --layout outputs/pickup-retry-reproduction/inputs/layout-1200.json --seed 1200 \
  --output outputs/pickup-retry-reproduction/g1-6 --wall-seconds 240 --max-layouts 4 \
  --total-proposals 4000 --proposals-per-layout 1000 --cluster-proposals 128 --max-steps 10000
```

按已有运行说明设置 Isaac 许可环境变量与 `LD_PRELOAD`。
分别替换 `--method g2/g3`、请求中的 `6/12` 和新的输出目录；
第七组是十二杂物 `g3 --disable-repair`。输出目录不能覆盖已有运行。
参考物理步数与原生策略的 200 次动作预算不同，此处不是原生策略预算内的评分证明。

## 边界

拾取语言前端、更多目标类型、冻结实验和真实策略比较仍未完成。
覆盖任务的场景感知杯腔/双臂规划仍需接入；其 G2 补全与物理验证不受本次修改影响。
若 G3 未触发修复或修复没有收益，就按实际证据报告，不继续增加模块寻找有利结果。
